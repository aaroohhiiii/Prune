# Round 2 Reflection

## 1. What was the most uncomfortable trade-off you made because of the time pressure?
The most uncomfortable trade-off was settling for a manual, admin-driven process for price updates instead of building a fully autonomous web scraping pipeline. Because of the tight deadline, I could not invest the necessary time to research and implement robust web scraping mechanisms (like Puppeteer/Playwright integrated with Vercel Cron) to automatically monitor the actual pricing pages of OpenAI, Anthropic, or Cursor. Scraping live DOMs is notoriously fragile, and building a system to reliably parse that data, handle CAPTCHAs, and manage edge cases would have consumed the hours I desperately needed to perfect the visual diff comparison UI and ensure all 10 automated Vitest suites passed. Instead, I traded true automation for a manual `/api/admin/pricing` endpoint where an admin must input the new prices themselves. This means the system is currently only as proactive as the human operating it, which feels like a significant compromise for a product built around "automated optimization".

## 2. If we extended the deadline by another 24 hours right now, what's the first thing you'd do?
With 24 more hours, I would refactor the pricing-detection system to use an async queue like Upstash QStash, decoupling heavy audit recomputation from the HTTP request lifecycle. Instead of processing everything synchronously through the GitHub Action, affected audits would be queued and recalculated in isolated workers, eliminating Vercel timeout risks and making the system scalable enough to handle thousands of users reliably. I’d also spend time improving the referral-and-earn feature with stronger technical logic and reward tracking.


## 3. Looking back at your Round 1 codebase as a now-experienced user of it: what's one thing your Round 1 self made harder for your Round 2 self?
My Round 1 self tightly coupled the core `runAudit` engine logic to static, hardcoded pricing constants. In Round 1, I assumed prices for tools like Claude or Cursor were immutable facts, so the engine directly referenced simple JSON arrays in `pricingData.ts`. When I started Round 2 and needed to dynamically calculate savings based on historical database snapshots versus live market shifts, this architectural decision became a massive roadblock. Instead of just passing a clean `pricingContext` object into the audit engine, I had to painfully untangle the engine's internal lookups, build an intermediate caching layer (`pricingService.ts`), and forcefully inject deep-cloned historical price states over the top of the user's original inputs just to get the math right. If I had decoupled the pricing data source from the calculation logic in Round 1, the Round 2 re-audit loop would have been trivial.
